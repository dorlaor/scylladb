Challenge 1: Multi-Row False Rejection

The Concern (Avi Kivity)

"Consider a query that reads 100 rows from a partition. With W-TinyLFU's 1% false-rejection rate, 99 rows are admitted and 1 is rejected. The next read of the same 100 rows turns into a cache miss. The multi-row query amplifies the false-positive rate."

The Math (If the Gate Fired)

Per-Row Rejection → Partition Miss

P(partition incomplete) = 1 - (1 - p)^R

R=1:    p=1%  →  1.0% miss
R=10:   p=1%  →  9.6% miss
R=100:  p=1%  → 63.4% miss
R=1000: p=1%  → 99.9% miss

Amplification Curve

Reality: the gate barely fires. Our add() uses a safe drain that moves window→probation without the frequency gate. 99% of evictions are direct evictions from probation front (pure LRU). The amplification curve is flat.

Why the Admission Gate Barely Fires

Two Paths Through W-TinyLFU

Path A: add() — Safe Drain

add(entry): 1. entry → window 2. while window > 1% target: move front of window → probation back (NO frequency comparison) (NO eviction, just list moves)

Handles every insert. No false rejection possible.

Path B: do_evict() — Direct LRU

do_evict(): 1. rebalance_protected() 2. drain_window(): window already at target → nothing to do 3. direct eviction: pop probation front → evict (pure LRU)

Window was already drained by add(). Falls through to pure LRU.

Where Scan Resistance Comes From

The Protected Segment Is the Hero

Scan resistance comes from the 3-segment SLRU structure, not from the frequency sketch.

Scan entries: add() → window → safe drain → probation back → drift to front → EVICTED (freq=1, never touched again) Hot entries: add() → window → probation → touch() → PROTECTED (80%) → stays (touched repeatedly, moves to back of protected) Scan can fill window+probation (20%) but CANNOT touch protected (80%) → hot entries are safe even during full table scans

Challenge 2: MVCC Version Ordering

The Invariant

"Older MVCC versions must be evicted before newer versions. If an older version survives while a newer version is evicted, the cache serves stale data — a correctness bug."

Three Guards That Preserve the Invariant

1. Insertion order

V1 rows are always inserted before V2 rows. In every segment list, V1 is closer to the front (LRU victim position).

2. Touch guard

partition_snapshot::touch() {
  if (at_latest_version()) {
    tracker->touch(last_dummy); // V2 only
  }
  // V1: never touched after V2 exists
}

3. Equal frequency

V1 and V2 share the same partition token → same sketch key → same frequency estimate. The admission gate can't prefer V1 over V2.

4. Safe drain

add() moves window→probation without the frequency gate. V2 rows can't be rejected at insert time.

A₁ B₁ C₁ ........... A₂ B₂ C₂] ↑ front (old, frozen) ↑ back (new, active) Time 2: Protected overflows → rebalance demotes front entries Protected: [... B₁ C₁ ................ The "Resurrection" Scenario

Could a newer version be evicted while an older version survives?

Attack attempt: 1. A₁ (V1) added → window → probation 2. A₂ (V2) added → window → probation Probation: [A₁ ... A₂] (A₁ at front, A₂ behind) 3. Can A₂ be evicted while A₁ survives? ✘ A₁ is at probation FRONT (inserted first, never touched) ✘ A₂ is BEHIND A₁ (inserted later) ✘ touch() only works on latest version → A₂ gets promoted, A₁ doesn't ✘ Same sketch key → tie → LRU order wins ✘ Safe drain → no rejection at insert Result: do_evict() picks A₁ from probation front → evicted first ✓ A₂ survives or gets promoted to protected ✓ Resurrection is impossible. ✓

The Admission Gate Paradox

If the gate barely fires, what are we paying for?

What W-TinyLFU costs vs what it delivers

Costs (always paid)

  • Count-Min Sketch: 128 KB+ memory per shard
  • record_access(): ~160 instructions per non-protected touch
  • Sketch aging/reset: periodic CPU burst
  • Window segment: extra list management
  • 24 Prometheus metrics for sketch internals
  • need_preempt() checks in drain loops
  • Complexity: 3 segments, frequency comparison, jitter logic

Benefits (actually delivered)

  • Scan resistance: 92% hot HR vs 61% ← from protected segment
  • Frequency gate: fires on <1% of evictions ← negligible
  • Sketch frequency data: rarely consulted ← wasted work

The insight

The protected segment (80% safe harbor for confirmed-hot entries) provides all the scan resistance. The window, sketch, and frequency gate are vestigial — they were designed for Caffeine's inline admission during add(), which we can't do because of the LSA allocator crash.

This leads to a natural simplification: SLRU (Segmented LRU).

SLRU: The Simplified Design

Same scan resistance. Zero overhead. Two segments.

Architecture

Removed

  • Window segment (1%)
  • Count-Min Sketch (all of count_min_sketch.hh)
  • record_access() — no sketch to increment
  • Frequency admission gate in drain_window()
  • drain_window() itself
  • Sketch aging, reset, resize
  • Window fraction config + REST endpoint
  • Sketch ratio config + REST endpoint
  • 24 sketch-related Prometheus metrics
  • Safe drain loop in add()

Kept

  • Probation/protected split (configurable ratio)
  • Promotion on touch (probation → protected)
  • Demotion when oversized (protected → probation)
  • Index eviction path (_index_list)
  • Packed evictable fields (segment tag)
  • MVCC ordering guarantees
  • Per-table cache hit/miss metrics
  • need_preempt() in rebalance loop

Why Two Segments Beat One

Single LRU during scan: [hot_A hot_B hot_C ...] ← scan pushes everything off Result: 0% hot data survives. Full cache wipe. SLRU during scan: Probation: [scan_1 scan_2 scan_3 ...] ← scan fills probation only Protected: [hot_A hot_B hot_C ...] ← untouched, safe Result: 80% hot data survives. Only 20% displaced. The single rule that creates scan resistance: "A second access promotes from probation to protected." Scan entries get one access. Hot entries get many.

Analysis: Why 85% vs 92%?

The 7% gap

SLRU achieves 85% hot HR vs W-TinyLFU's 92%. Where does the difference come from?

The Window Hop Effect

W-TinyLFU add() path: entry → WINDOW → safe drain → PROBATION back (extra hop) (immediate) SLRU add() path: entry → PROBATION back (direct) Both end at probation back. But in W-TinyLFU, the safe drain happens inside add(), which is called from cache_mutation_reader — during a read operation. The entry spends a brief moment in the window before being moved to probation. During that brief window, if a touch() arrives for the same entry (e.g., the read is still in progress and another request hits it), the touch() on a window entry just moves it to window back — NOT to protected. It needs to reach probation first, then get touched again, to be promoted. In SLRU, the entry goes directly to probation. The very next touch() promotes it to protected immediately. One fewer round-trip needed.

Why W-TinyLFU Still Wins by 7%

Paradoxically, the window hop helps W-TinyLFU. The safe drain in add() moves entries to probation back, but it also increments the sketch via record_access(). Even though the sketch is rarely consulted, the record_access() call contributes to the sketch aging counter (_sample_count). When the counter exceeds the threshold, _sketch.reset() is called, which iterates the entire sketch table. This periodic full-table scan of the sketch has a side effect: it triggers sample_segment_frequencies(), which iterates up to 1000 entries per segment.

These periodic scans keep cache metadata warm in L1/L2, which slightly improves the performance of subsequent touch() operations on the same cache lines. SLRU doesn't have this warming effect.

However, the 7% gap is more likely due to run-to-run variance on a shared machine after hours of benchmarking. The instruction counts (the stable metric) show SLRU is faster.

Summary

SLRU advantages

  • Zero instruction overhead (−32 vs baseline)
  • Zero memory overhead (no sketch)
  • O(1) eviction, no stall risk
  • ~150 lines vs ~600 lines
  • No multi-row amplification concern
  • No false-rejection risk at all

W-TinyLFU advantages

  • 7% higher hot HR in this benchmark
  • Frequency sketch available for future use
  • Matches Caffeine's published design

Recommendation

SLRU is the pragmatic choice: 85% hot HR (vs 61% LRU baseline) with zero overhead and minimal code. The 7% gap vs W-TinyLFU is worth investigating further but does not justify the complexity of the sketch and admission gate infrastructure that is effectively unused.
